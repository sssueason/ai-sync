# ALIGN — 初始化对齐（先看后做）

> 用途：**首次接入一台机器**、或大改动之后，让"本机权威树 ↔ 云端镜像 ↔ 其它机器"收敛。
> 铁律：**默认只报告，不改任何文件**；改动数据只在 `--apply` 且你看过计划之后。

---

## 一条命令

```bash
node <引擎根>/tools/sync-align.mjs            # 计划（默认）——只读
node <引擎根>/tools/sync-align.mjs --apply    # 执行
node <引擎根>/tools/sync-align.mjs --set keti-text --apply   # 只处理某个集合
```

退出码：`0` = 无待处理 / 执行成功；`2` = 计划模式下有待拉或冲突（"该动手了"）；`3` = 出错（看 `[FAIL]` 行）。

## 计划模式输出长什么样

```
=== 初始化对齐（仅计划）· <机器> ===
  仓库 vault: exists=true dirty=0 behind=0 ahead=0
  仓库 <实例仓>: exists=true dirty=0 behind=0 ahead=0
  镜像计划: 待推=0 待拉=1 冲突=0 一致=19927
  待处理 1 项 → 确认后跑：node tools/sync-align.mjs --apply
```

| 字段 | 含义 | 你该做什么 |
|---|---|---|
| `behind`（git 仓） | 远端有新提交 | 跑一次 tick（或 `sync.ps1 pull`） |
| `ahead` | 本地有未推提交 | 跑一次 tick（或 `sync.ps1 push`） |
| `待推(seed)` | 本机权威目录里有、镜像里没有 | `--apply` 会 seed 过去 |
| `待拉` | 镜像里有、本机权威目录没有（**对侧新增**） | `--apply` 会拉进权威目录 |
| `冲突` | 两边都改过同一文件 | `--apply` 后**败者落侧车**，你要看一眼 |
| `一致` | 大小相同（`-Hash` 时逐字节校验） | 不用管 |

## 执行模式做了什么（顺序很重要）

1. `tree-sync -Apply`：**镜像 → 本机权威树**（三方合并，冲突落侧车）
2. `seed-mu2`：**本机权威树 → 镜像**（Windows 用 robocopy；macOS 的 rsync 版尚未实现，会打印明确注记）

顺序与日常重活 `daily.ps1` 一致：先入后出，避免"刚推上去又被拉回来"。

## 冲突文件长什么样

```
<权威目录>/某文档.docx
<权威目录>/某文档.local-<机器>-<日期>.docx   ← 败者（另一台机器的版本）
```

- **没有文件被删除**，也没有被静默覆盖。
- 处理：打开两份比一下 → 留对的那份 → 把 `.local-*` 那份删掉。
- `sync-align` 会把冲突数报出来；`sync-status` 也会把它列进待办。

## 什么时候需要跑

| 场景 | 跑什么 |
|---|---|
| 新机器第一次接进来 | `--plan` 看 → `--apply` |
| 换了同步空间根目录 | 先改 `machines/<机器>.json` 的 `mu2.dest` → `--plan` → `--apply` |
| 补了新的 set（新的文件夹范围） | `--plan`（通常显示大量"待推"，正常）→ `--apply` |
| 对端机器重装过、状态不明 | `--plan`，按字段决定 |
| 日常 | **不用跑**。tick 每 N 分钟做 µ1，重活每天 1–2 次做 µ2 |

## 常见疑问

**Q：`--apply` 会不会把我的改动冲掉？**
A：不会。合并规则是"两边都变 → mtime 新者胜 + 败者另存"。唯一会覆盖的场景是"只有一边变了"——那正是你要的同步。

**Q：为什么不在 tick 里自动 `--apply`？**
A：因为会改本地文件。tick 是 5 分钟级的无人值守动作，只做 git（可合并、可回滚）。镜像合并在 `daily` 里自动跑（1–2 次/天），人工重装/换盘这类场景才需要手跑 `align`。

**Q：计划模式会不会因为读文件而改变 mtime？**
A：不会。计划模式只读元数据（`-Hash` 时才逐字节读内容，也不写）。
